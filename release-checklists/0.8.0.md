# Mixle 0.8.0 release-preparation checklist

This is the authoritative package-local checklist for 0.8.0. The release contract is defined by
`docs/release-readiness.rst`; supporting decisions, risks, review protocols, and stage gates are in this
directory. The former link to an ignored `notes/` worklist was removed because a release process must be
available from a clean clone.

Preparation branch: `release-prep/0.8.0` → `release/0.8.0`.

**Do not create `v0.8.0`, publish artifacts, merge the preparation PR, or mark final sign-off while any
pre-publication `IMPLEMENTED`, `HOSTED`, or `EXTERNAL` gate below remains.** `POST-RELEASE` rows are mandatory follow-up
checks after publication; by definition they neither authorize nor block the first publication. The tag is
deliberately outside this work.

## Status vocabulary

- `IMPLEMENTED` — implementation exists and has local development checks, but this is not
  candidate-bound release evidence and does not clear the gate.
- `DONE` — a schema-validated receipt records the command, its measured result, the date, the commit
  the measurement ran on, and an evidence digest of the candidate's tracked content excluding the
  receipts directory. The digest, not the commit, is what binds the receipt: requiring a committed
  receipt to name the SHA of the commit containing it was unsatisfiable and is why no receipt existed
  before 2026-08-22 (D-0193 BLOCKER 2, resolved in D-0195). Change any tracked file outside
  `0.8.0-receipts/` and every receipt stops validating.
- `HOSTED` — implementation exists; the exact final commit must pass the named hosted job.
- `EXTERNAL` — requires a human reviewer, external user, registry, or designated hardware.
- `EXCLUDED` — claim or operation is intentionally omitted, with the limitation stated.
- `POST-RELEASE` — can run only after publication.

The release-owner transition is: close every pre-publication gate → approve the exact
`release/0.8.0` tip → create its signed annotated `v0.8.0` tag → publish the GitHub Release. The publish
workflow then independently re-verifies the version, signed tag, exact release-branch tip, required check
runs, and artifact digests before Trusted Publishing. A successful upload changes the applicable
`POST-RELEASE` rows from pending follow-up to blocking completion work; failure of a post-release check
requires the documented yank-or-patch-forward decision.

Local validation commands are individually capped at 30 seconds. Broad suites and the full Sphinx build belong
in hosted CI; timing out locally is not converted into a pass.

## Appendix: Risk register (formerly `0.8.0-risks.md`)

## 0.8.0 Release Risk Register

Live, ranked register of the risks to shipping 0.8.0 (worklist **G0.5**). Reviewed weekly; **every high
risk must have an active mitigation or an explicit release limitation** recorded here. Each entry:
**probability · impact · mitigation · trigger · owner**. Ranked by probability × impact (highest first).

Owner defaults to the release owner (grant.boquet@gmail.com). "Mitigation" links to the gate or decision
that reduces the risk; a gate in an open PR is not yet in effect on `release/0.8.0`.

---

### R-01 · Independent review bottleneck — **HIGH**

- **Probability:** high · **Impact:** high (blocks the entire release; the work is done but unreviewed).
- **Now:** most implementation work is integrated. Final credibility still depends on reviewers and release
  testers who are independent of the implementation author; a green self-reviewed branch is not E4 evidence.
- **Mitigation:** keep remaining release changes single-purpose, retain exact-tip evidence, and recruit the
  statistical, systems, and clean-install reviewers required by §15 of the release checklist.
- **Trigger:** the release branch has not advanced in a week, or open-PR count is not trending down.
- **Owner:** release owner.

### R-02 · Merge conflicts among concurrent release PRs — **MEDIUM**

- **Probability:** medium · **Impact:** medium (rework, not a shipped defect).
- **Now:** the historical stack has been reconciled. Concurrent repairs can still overlap manifests,
  workflow files, ``pyproject.toml``, and ``conftest.py``.
- **Mitigation:** use isolated branches, merge the current release tip into each PR without rewriting shared
  history, regenerate manifests from the combined tree, run focused checks, and integrate one PR at a time.
- **Trigger:** a merge reports a conflict in a shared file.
- **Owner:** release owner.

### R-03 · API churn surprises users — **MEDIUM-HIGH**

- **Probability:** medium · **Impact:** high (a behavior change breaks a user's script silently).
- **Now:** this cycle changes defaults (`optimize`/`fit`/`best_of` quiet-by-default), floors (drop Python
  3.10), and introduces deprecations.
- **Mitigation:** the deprecation policy (warn, keep ≥2 minor releases) and the decision log entries
  D-0001/D-0003/D-0004; each behavior change is called out in its PR body and the changelog.
- **Trigger:** a changelog entry for a behavior change is missing, or a rename ships without a deprecation.
- **Owner:** release owner.

### R-04 · Clean-wheel / base-install regression — **MEDIUM**

- **Probability:** medium · **Impact:** high (the package doesn't import for a plain user).
- **Mitigation:** the blocking clean-wheel install + import-sweep job, the base-install optional-import
  guard, and the collection-hygiene gate (heavy frameworks stay behind `importorskip`).
- **Trigger:** the clean-wheel job fails, or a new top-level optional import lands.
- **Owner:** release owner.

### R-05 · Optional-dependency breakage — **MEDIUM**

- **Probability:** medium · **Impact:** medium (a `pip install mixle[x]` fails or downgrades a core dep).
- **Mitigation:** the extras resolver matrix (`pip install .[extra]` + `pip check` per extra) and the
  min-versions job.
- **Trigger:** a cell in the extras matrix goes red, or `pip check` reports a conflict.
- **Owner:** release owner.

### R-06 · Stochastic / numerical flakiness — **MEDIUM**

- **Probability:** medium · **Impact:** medium (a flaky gate erodes trust or blocks unrelated PRs).
- **Mitigation:** per-test global-state isolation (pinned by the order-independence test), fixed seeds
  (random-state discipline), the numerical stress panel, and generous pinned thresholds.
- **Trigger:** a test passes locally but flakes in CI, or fails only under a different worker order.
- **Owner:** release owner.

### R-07 · Backend claims outrun hardware evidence — **MEDIUM**

- **Probability:** medium · **Impact:** high (a false "runs on any backend at scale" claim).
- **Mitigation:** the backend support matrix with honest per-backend status; TP/PP/CP raise when requested
  but not integrated; frontier-training surfaces labeled as prototypes; README overclaims qualified.
- **Trigger:** a doc or README describes a backend/scale as supported without CI or hardware evidence.
- **Owner:** release owner.

### R-08 · Serialization incompatibility — **MEDIUM**

- **Probability:** low-medium · **Impact:** high (a saved model won't load in the new version).
- **Mitigation:** cross-version load fixtures (0.7.0 artifacts), atomic artifact writes, and safe-JSON
  deployment for pure models.
- **Trigger:** the cross-version fixtures test fails, or a manifest schema field changes without a fixture.
- **Owner:** release owner.

### R-09 · Benchmark irreproducibility — **LOW-MEDIUM**

- **Probability:** low-medium · **Impact:** medium (a perf claim can't be reproduced).
- **Mitigation:** the benchmark harness is tracked in git; benchmark-methodology changes get a decision-log
  entry; stale result files are archived and 0.8.0 makes no numerical performance claim without a retained
  exact-candidate run.
- **Trigger:** a benchmark number in docs has no runnable harness behind it.
- **Owner:** release owner.

### R-10 · Test-suite runtime prevents frequent execution — **LOW-MEDIUM**

- **Probability:** low-medium · **Impact:** medium (slow gates get skipped, letting regressions in).
- **Mitigation:** local work selects focused checks with a hard 30-second command limit; broad fast, full,
  optional, and platform matrices run in hosted workflows. Collection stays lean in the base environment.
- **Trigger:** routine local validation cannot be scoped below 30 seconds, or hosted lanes stop running.
- **Owner:** release owner.

### R-11 · Stale documentation from older branches — **LOW**

- **Probability:** low · **Impact:** medium (docs describe behavior that shipped differently).
- **Mitigation:** docs build in CI; the claim-evidence ledger and "What Mixle Is Not" page bound claims;
  the maturity registry/manifest is drift-gated against the maturity doc.
- **Trigger:** a docs build references a removed symbol, or a claim has no ledger row.
- **Owner:** release owner.

### R-12 · Related-project version skew — **EXCLUDED FROM 0.8.0**

- **Probability:** low · **Impact:** medium (a sibling pins an incompatible `mixle`).
- **Now:** Core 0.8.0 is a standalone release and makes no compatibility or co-install claim for
  related projects, so their version skew cannot block or be cleared by this release.
- **Mitigation:** a future coordinated release must add a versioned family manifest and exact
  co-install receipts before making a family claim.
- **Trigger:** public Core 0.8.0 prose implies an included sibling or coordinated compatibility.
- **Owner:** release owner (family-level).

## 0.8.0 backend execution evidence

Retained execution evidence for the distributed backends `docs/backend-support.rst` labels
**"Tested, not CI-gated"** — MPI, Spark, Ray and Lightning — plus the optional-CI routes. That label
exists because those backends are installed in no CI lane, so a regression in them would not be
caught automatically. This file is the counterpart the label asks for: the backends were actually
run, on a real installation, and the commands and versions are recorded so the run can be repeated.

### What this is, and what it is not

This is **implementer-produced execution evidence**, not an independent systems review. It records
that the routes execute and agree with the local backend on this machine. It does **not** discharge
the E14.3 systems-review gate, which requires a reviewer other than the implementer working from a
clean clone, and which explicitly states that one local backend cannot clear it.

Read it as: "these backends were exercised and this is exactly how" — not "these backends are
certified."

#### MPI numerical agreement, run directly under `mpiexec`

The backend-matrix tests assert agreement internally; this is the same claim made visible, because
"scale with a flag" is only worth anything if the distributed fit equals the local one:

```
mpiexec -n 2 python mpi_probe.py

  ranks=2  local=(4.9428960096, 3.9056520032)  mpi=(4.9428960096, 3.9056520032)
  agree to 1e-10: True
```

A Gaussian fit over 400 observations, two ranks, tree-fold reduction of sufficient statistics.
Exact agreement with the serial fit to 1e-10 on both parameters.

### GPU (Metal / MPS) — it runs, and it does NOT match CPU

This machine is an Apple M4 (10 GPU cores). `torch.backends.mps.is_available()` is true;
**CUDA is not available on this machine**; Metal is a different backend and the evidence in this
section says nothing about CUDA. CUDA execution evidence was later produced separately (2026-08-05)
on a rented RTX 3060 — driver 580.126.09, torch 2.5.1+cu124 — and committed as
`0.8.0-cuda-receipt.json`: `gmm_float32_cpu_vs_cuda` divergence 0.0, `hmm_float32_cuda` passes,
`quantized_parity` passes. Getting there required fixing two real CUDA-only defects
(`TorchEngine.index_add` and `matmul`/`stack`/`concatenate` ingestion did not enforce the declared
dtype policy; CPU/MPS silently promote mixed float32/float64 where CUDA hard-errors), which is
exactly why an execution receipt and not an assumption is the standard. The `Torch (CUDA / GPU)`
row is *Hardware-gated: executed once, receipt retained, not CI-gated*.

What was verified is the `Torch (CPU)` row's claim that GPU is reachable "via device argument":

```python
NeuralDensityEstimator(build_vae(4, latent=2), device="mps")
optimize(data, est, max_its=3)      # fit completes; parameters live on mps:0
```

That works. But the GPU and CPU paths **do not agree numerically**, and the gap is larger than a
reader would assume. Same seed, same architecture, same data; total per-observation log-density
compared across devices:

| optimizer iterations | max abs difference | max relative |
|---|---|---|
| 1 | 1.91e-01 | **2.2e-02** |
| 3 | 2.48e-01 | 3.4e-02 |
| 10 | 3.39e-01 | 4.2e-02 |

The divergence is already ~2% relative after a *single* iteration and grows only mildly after that,
so this is not chaotic amplification of a tiny difference through the optimizer — it is a
kernel-level float32 difference between the MPS and CPU implementations, present from the first
step, with mild accumulation on top.

Consequences, stated plainly:

* A GPU fit is **not** a drop-in reproduction of a CPU fit. Anything that pins a log-density, a
  fitted parameter, or a model digest computed on CPU will not match the same computation on MPS.
* `mixle.inference.reproduce` fingerprints parameters, so a receipt recorded on one device will not
  verify on the other. That is correct behaviour — the fits genuinely differ — but it is a trap if a
  user assumes `device=` is a performance knob rather than a numerical one.
* Any future promotion of a GPU row needs a stated **tolerance**, not an equality claim.

This was not previously measured or documented. It is recorded here rather than in the support
matrix's claim columns because it is a property of the torch/MPS stack, not a mixle defect.

### Limits of this evidence — read these before citing it

* **One machine, one OS, one architecture.** macOS arm64. Nothing here says anything about Linux
  x86_64, which is the platform the CI baseline and most users run.
* **One process topology.** Every "distributed" run here is multi-process on a single host. No
  multi-node run and no real network transport. `docs/backend-support.rst` already places
  frontier-scale multi-node/multi-GPU training out of scope for 0.8.0, and this evidence does not
  extend it.
* **No interruption, corruption, or rollback testing.** The systems-review protocol requires
  checkpoint interruption/recovery, corrupted-artifact rejection and rollback behaviour. Those are
  not covered here.
* **Not independent.** See the note at the top.

### Reproducing it

The backends are not in the release venv; they are installed in the development environment at
`mixle/.venv` (Python 3.12.12). Point `PYTHONPATH` at the candidate worktree and use that
interpreter. `MIXLE_RUN_TORCHRUN_SMOKE=1` is required to un-gate the torchrun smoke tests, which
skip by default.
