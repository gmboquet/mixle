# Mixle 0.8.0 release-preparation checklist

This is the authoritative package-local checklist for 0.8.0. The release contract is defined by
`docs/release-readiness.rst`; supporting decisions, risks, review protocols, and stage gates are in this
directory. The former link to an ignored `notes/` worklist was removed because a release process must be
available from a clean clone.

Preparation branch: `release-prep/0.8.0` → `release/0.8.0`.

**Do not create `v0.8.0`, publish artifacts, merge the preparation PR, or mark final sign-off while any
pre-publication `IMPLEMENTED`, `HOSTED`, or `EXTERNAL` gate below remains.** `POST-RELEASE` rows are mandatory follow-up
checks after publication; by definition they neither authorize nor block the first publication. The tag is
deliberately outside this work.

## Status vocabulary

- `IMPLEMENTED` — implementation exists and has local development checks, but this is not
  candidate-bound release evidence and does not clear the gate.
- `DONE` — a schema-validated receipt records the exact candidate SHA, command, measured result,
  and date.
- `HOSTED` — implementation exists; the exact final commit must pass the named hosted job.
- `EXTERNAL` — requires a human reviewer, external user, registry, or designated hardware.
- `EXCLUDED` — claim or operation is intentionally omitted, with the limitation stated.
- `POST-RELEASE` — can run only after publication.

The release-owner transition is: close every pre-publication gate → approve the exact
`release/0.8.0` tip → create its signed annotated `v0.8.0` tag → publish the GitHub Release. The publish
workflow then independently re-verifies the version, signed tag, exact release-branch tip, required check
runs, and artifact digests before Trusted Publishing. A successful upload changes the applicable
`POST-RELEASE` rows from pending follow-up to blocking completion work; failure of a post-release check
requires the documented yank-or-patch-forward decision.

Local validation commands are individually capped at 30 seconds. Broad suites and the full Sphinx build belong
in hosted CI; timing out locally is not converted into a pass.

### GPU (Metal / MPS) — it runs, and it does NOT match CPU

This machine is an Apple M4 (10 GPU cores). `torch.backends.mps.is_available()` is true;
**CUDA is not available on this machine**; Metal is a different backend and the evidence in this
section says nothing about CUDA. CUDA execution evidence was later produced separately (2026-08-05)
on a rented RTX 3060 — driver 580.126.09, torch 2.5.1+cu124 — and committed as
`0.8.0-cuda-receipt.json`: `gmm_float32_cpu_vs_cuda` divergence 0.0, `hmm_float32_cuda` passes,
`quantized_parity` passes. Getting there required fixing two real CUDA-only defects
(`TorchEngine.index_add` and `matmul`/`stack`/`concatenate` ingestion did not enforce the declared
dtype policy; CPU/MPS silently promote mixed float32/float64 where CUDA hard-errors), which is
exactly why an execution receipt and not an assumption is the standard. The `Torch (CUDA / GPU)`
row is *Hardware-gated: executed once, receipt retained, not CI-gated*.

What was verified is the `Torch (CPU)` row's claim that GPU is reachable "via device argument":

```python
NeuralDensityEstimator(build_vae(4, latent=2), device="mps")
optimize(data, est, max_its=3)      # fit completes; parameters live on mps:0
```

That works. But the GPU and CPU paths **do not agree numerically**, and the gap is larger than a
reader would assume. Same seed, same architecture, same data; total per-observation log-density
compared across devices:

| optimizer iterations | max abs difference | max relative |
|---|---|---|
| 1 | 1.91e-01 | **2.2e-02** |
| 3 | 2.48e-01 | 3.4e-02 |
| 10 | 3.39e-01 | 4.2e-02 |

The divergence is already ~2% relative after a *single* iteration and grows only mildly after that,
so this is not chaotic amplification of a tiny difference through the optimizer — it is a
kernel-level float32 difference between the MPS and CPU implementations, present from the first
step, with mild accumulation on top.

Consequences, stated plainly:

* A GPU fit is **not** a drop-in reproduction of a CPU fit. Anything that pins a log-density, a
  fitted parameter, or a model digest computed on CPU will not match the same computation on MPS.
* `mixle.inference.reproduce` fingerprints parameters, so a receipt recorded on one device will not
  verify on the other. That is correct behaviour — the fits genuinely differ — but it is a trap if a
  user assumes `device=` is a performance knob rather than a numerical one.
* Any future promotion of a GPU row needs a stated **tolerance**, not an equality claim.

This was not previously measured or documented. It is recorded here rather than in the support
matrix's claim columns because it is a property of the torch/MPS stack, not a mixle defect.

### Limits of this evidence — read these before citing it

* **One machine, one OS, one architecture.** macOS arm64. Nothing here says anything about Linux
  x86_64, which is the platform the CI baseline and most users run.
* **One process topology.** Every "distributed" run here is multi-process on a single host. No
  multi-node run and no real network transport. `docs/backend-support.rst` already places
  frontier-scale multi-node/multi-GPU training out of scope for 0.8.0, and this evidence does not
  extend it.
* **No interruption, corruption, or rollback testing.** The systems-review protocol requires
  checkpoint interruption/recovery, corrupted-artifact rejection and rollback behaviour. Those are
  not covered here.
* **Not independent.** See the note at the top.
