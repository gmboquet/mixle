## Confirmed blocking / major

- **[T1-01, blocking]** `GeneralizedParetoEstimator` with a `pseudo_count` prior and ZERO raw
  observations (a prior-only cold start, or an EM component that received zero responsibility in a
  batch — a realistic state, not a synthetic edge case) returned a qualitatively wrong fit (shape
  sign-flipped, scale unrelated to the prior) at an extreme threshold. Root cause: the correctly
  computed, cancellation-free `prior_variance` payload was discarded whenever the shift-anchored
  track never activated (which is unconditional at zero raw observations), falling back to raw
  differencing at threshold magnitude — exactly the cancellation the payload exists to avoid.
- **[T4-01, major]** `GeneralizedParetoAccumulator.combine()` on a foreign/plain-tuple partial at a
  realistic large-magnitude threshold (e.g. Unix-timestamp scale) produced a badly wrong, degenerate
  fit with `numerical_repairs()` reporting nothing. Root cause: the same raw-moment-cancellation
  fallback as T1-01, compounded by an earlier, unrelated degenerate short-circuit that returned
  before the T1-02/D-0206 support-consistency-unverified disclosure branch ever ran. A 200-seed
  sweep during the fix confirmed the failure isn't limited to the filed shape=0.0 example.
- **[T1-02, major]** `glm(..., robust='HC2'/'HC3')`'s leverage computation reintroduced the exact
  squared-condition-number instability a neighboring "audit B4" fix already avoids elsewhere in the
  same function, producing leverage values outside `[0, 1]` and a false-positive "singleton
  observation" refusal at realistic high-collinearity condition numbers (~1e9), on a design with no
  dummy/discrete coding at all.
- **[T2-01, major]** `optimize()`'s auto-inference freezes an identifier-like/high-cardinality column
  into a categorical that scores `-inf` on any unseen value, undisclosed at `optimize()`'s own public
  docstring (the policy existed only in an internal docstring that explicitly said as much) and
  unguarded by `Model.evaluate()`, which checks `isnan`/`isposinf` but not `isneginf`.
- **[T3-01, filed major, re-verified as minor]** `to_json()`/`from_json()` cannot round-trip any
  family in `mixle.stats.directional` or `mixle.stats.matrix` (12 families across two whole modules,
  not just the single `VonMisesDistribution` example the docstring/CHANGELOG name). The verifying
  skeptic independently confirmed the technical claim in full (and found two more families the
  original tester couldn't build test data for) but downgraded severity after confirming
  `Model.deploy()`/`Model.load()`'s pickle fallback handles this correctly and discloses it three
  ways — the production path is safe; this is a documentation-completeness gap, not a functional
  defect.

## The pattern, a fourth time: the fix wave's own diff needed a second pass

After all four fixes landed, an independent agent adversarially reviewed the full production-code
diff before this candidate was built — now a practice with a confirmed track record across three
consecutive campaigns. It found one confirmed-blocking regression: the T1-02 GLM leverage fix
(`hat_diag = sum(u * u, axis=1)`, read directly off the SVD's `U`) is correct only for a full-rank
design. `xtwx_inv` already masks out insignificant singular directions; the unmasked `U`-based
leverage sums to the column count `p` instead of the effective rank `r` for a genuinely
rank-deficient design (collinear or duplicated columns, not merely ill-conditioned) — reintroducing
the exact false-positive refusal the fix was written to eliminate. Confirmed with a direct
old-code-vs-new-code repro (a 9-row, rank-4 design built from 3 predictors duplicated 3x). Fixed by
masking `hat_diag` with the same `significant` singular-value flag `xtwx_inv` already applies — a
no-op for the full-rank case the fix's own test suite covered, correct for the rank-deficient case
it missed. Regression test proven to fail against the pre-fix code and pass after; full existing GLM
suite (135 tests) re-verified green; the singleton-dummy-level refusal the original fix exists to
catch was re-confirmed still firing correctly (the guard was not widened away).

The other three commits in this wave (T1-01/T4-01's GeneralizedPareto fix, T2-01's disclosure fix,
T3-01/T3-05's documentation-only fix) survived the same adversarial review with no confirmed gap —
the reviewer independently re-derived and probed several scenarios beyond the fixing agents' own
shipped tests for each (an ordinary no-prior fit, a same-factory trustworthy-max combine, a `.loc`
retarget with zero observations, propose()'s actual call graph traced directly rather than trusted
from the fixing agent's report) and found the fixes hold.

## Documentation and minor findings reported

- (T1) `GeneralizedPareto`'s prior + `.loc` retarget + foreign-combine composition still ends with a
  live, unclamped support inconsistency when the tracked max is untrusted — correctly disclosed via
  `numerical_repairs()` by design, but a passive string a caller must explicitly read, not a
  `warnings.warn()`.
- (T2) `GeneralizedParetoAccumulator.combine()` raises a bare `IndexError` on a malformed/wrong-arity
  tuple rather than a message naming the expected shape.
- (T2) `pandas_source.py`'s `column_records()` docstring describes a "KNOWN GAP" that could not be
  reproduced — the code appears to already handle it correctly and the docstring is stale.
- (T2) Default `repr`s for a `Solution` and for a fitted model wrapping a high-cardinality categorical
  dump every training row / every category verbatim.
- (T3) `to_json()`'s error message for `MallowsDistribution` leaks an internal, undocumented class
  name (`MallowsFitDiagnostics`) rather than the cleaner "write-only" refusal other families hit.
- (T3) `to_json()`/`from_json()` round-trips normalize numpy scalar types to plain Python types, so
  `repr()` can differ before/after even though values and `log_density` match exactly — cosmetic.
- (T3) README's "deep catalog" bullet does not caveat that directional/matrix families are
  JSON-incapable (closed alongside T3-01 by the same docstring fix).
- (T4) `LDAEstimator`'s default alpha solver deterministically hits its "diverging to infinity"
  boundary for realistic small corpora (5-19 documents) across every seed tried; the constructor
  docstring for `fixed_alpha`/`alpha_threshold` doesn't hint this is common.
- (T4) `TreeHiddenMarkovEstimator`'s empty-tree rejection message doesn't distinguish itself from the
  sibling families' tolerated empty-sequence case, worth a clearer message.
- (T4) The `GeneralizedPareto` raw-moment-cancellation warning's first suggested remedy ("accumulate
  through this family's own accumulator") reads as though the caller wasn't already using it, when
  the documented, supported trigger (T1-02's own regression test) is calling that exact accumulator's
  `.combine()` with an externally-built partial.
