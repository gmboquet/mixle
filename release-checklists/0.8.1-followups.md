# mixle 0.8.1 patch follow-ups

Findings from the two independent release testers run against the 0.8.0 release candidate
(`dd167be2b09e2ee9062a34b6c290fa5d5e29aede`), deferred to a 0.8.1 patch by explicit release-owner
decision rather than blocking 0.8.0 (D-0210). None of these are regressions from the 0.8.0
release-prep work itself — they are pre-existing characteristics of code the release-prep effort
never touched, surfaced specifically because this was the first time either distribution family
was exercised by a tester with no foreknowledge of the implementation.

Each item lists: what's wrong, why it matters, a suggested fix direction, and which tester found it.
None of these have been independently re-verified against source beyond what's noted — treat the
"suggested fix" as a starting hypothesis for whoever picks this up, not a prescribed patch.

## Blocking-severity (recommend fixing before 0.8.1 ships)

### FU-01 · `BradleyTerryDistribution`/`DavidsonDistribution.log_density` returns a joint density, not a win probability
**Tester B.** `log_density((i, j))` reads, from its docstring, like it returns log P(i beats j). It
does not: `exp(log_density((i,j))) + exp(log_density((j,i)))` sums to `1/C(K,2)`, not 1 — it's the
joint density over (which pair was compared, drawn uniformly from all pairs) × (who won).
Independently verified in this session:
```python
p_ij = math.exp(dist.log_density((i, j))); p_ji = math.exp(dist.log_density((j, i)))
# p_ij + p_ji == 1/C(K,2), not 1
```
A caller computing `exp(log_density(...))` expecting a win probability gets a plausible-looking
(it's in [0, 1]) but silently wrong number, off by a factor of `C(K,2)`, no error or warning.
**Suggested fix:** add an explicitly-named `win_probability(i, j)` (or similar) computing the
correct conditional (`sigmoid(log_w_i - log_w_j)` for Bradley-Terry; the Davidson/Rao-Kupper
analogues for their families), and tighten `log_density`'s own docstring to state precisely what
it returns. Affects `mixle/stats/rankings/bradley_terry.py` and likely
`mixle/stats/rankings/paired_comparison.py` (Davidson/Rao-Kupper share the same pattern per the
tester's report).

### FU-02 · `numerical_repairs()` misses a shape-parameter clamp at tiny n (GeneralizedPareto)
**Tester A.** `GeneralizedParetoEstimator`'s `xi_min=-10.0` floor fires in 31/1600 scanned tiny-n
cases (n in {3,4,5,6}, 400 seeds each); in every one of those 31, `numerical_repairs()` reports
nothing, or reports only a co-occurring scale-floor repair, never the shape clamp itself — even
though the same mechanism correctly reports scale floors alone when only that fires. A confidently
reported `shape=-10.0` (implying a short tail) with no disclosure is the opposite of what
`numerical_repairs()` exists to prevent. Matches the "floor-disclosure" pattern already fixed this
release for several other families (`GaussianEstimator._record_variance_floor` and its siblings —
see D-0209) — this looks like the same gap, unaddressed in GeneralizedPareto's shape-clamp path
specifically. **Suggested fix:** extend the existing floor-disclosure mechanism to cover the
`xi_min` clamp in `mixle/stats/univariate/continuous/generalized_pareto.py`.

### FU-03 · `optimize()` can silently stop far short of `max_its` with no warning
**Tester A.** Fitting a 2-component GPD mixture with `max_its=2000, delta=1e-8` actually ran only 2
EM iterations and stopped with `converged=False` and `objective_gain=16.9` (nowhere near settled).
Zero warnings were emitted. This is a *different* code path from hitting the `max_its` cap, which
does warn (confirmed elsewhere in this same session) — so a user who has learned "no warning means
either it converged or I'll get the documented cap warning" will miss a silently-truncated,
unconverged fit entirely unless they manually check `fit_provenance().iterations` against
`max_iterations` on every call. **Suggested fix:** find whatever early-exit condition stopped EM at
iteration 2 despite `converged=False`, and either fix the exit condition or emit the same class of
warning the max-its-cap path already emits. Scope is unclear without investigation — this may be
narrow (specific to this mixture configuration) or a broader EM-loop gap; needs scoping before
estimating fix size.

### FU-04 · `pit_values` misattributes a `TypeError` as an unrelated `ValueError`
**Tester A.** `GeneralizedParetoDistribution.cdf` is scalar-only (confirmed via
`inspect.signature`); `mixle.inference.ks_1samp`'s own docstring types its `cdf` argument as
vectorized (`Callable[[np.ndarray], np.ndarray]`). Passing a fitted GPD's `.cdf` into `ks_1samp` (a
completely natural "test my fit" move) raises `TypeError: only 0-dimensional arrays can be
converted to Python scalars`. The sibling function `pit_values` catches that same failure
internally and re-raises it as `ValueError("cdf must return finite values matching y")` — actively
misleading a debugging user toward the wrong cause (source-confirmed by the tester, not just
observed behavior). **Suggested fix, two parts:** (1) fix `pit_values`'s exception handling to not
misattribute a callable-signature `TypeError` as a values/shape `ValueError`; (2) separately decide
whether `GeneralizedParetoDistribution.cdf` (and presumably its siblings) should accept array input
to match what `ks_1samp`'s own docstring promises, or whether `ks_1samp`'s docstring should instead
tell callers to wrap with `np.vectorize` first.

## Non-blocking but real (recommend fixing, lower urgency)

### FU-05 · Mixed tie/no-tie tuple shapes raise a raw numpy error instead of a clean validation message
**Tester B.** Feeding `BradleyTerryEstimator` a dataset that mixes 2-tuples (no tie) and 3-tuples
(with tie) — the natural mistake of forgetting to strip draws before calling the no-tie estimator —
raises `ValueError: setting an array element with a sequence. The requested array has an
inhomogeneous shape...`, a raw numpy internals message. The same encoder already produces clean,
specific, row-numbered messages for self-comparisons and out-of-range indices, and for
uniformly-wrong arity (`"...must have shape (N, 2)"`) — it's specifically the *mixed*-arity case
that falls through. **Suggested fix:** add an explicit arity-consistency check in the Bradley-Terry
data encoder ahead of the numpy conversion.

### FU-06 · Inconsistent exception type for the same identifiability failure across ranking families
**Tester B.** The unregularized MLE-divergence failure raises `ValueError` for Bradley-Terry and
Thurstone-Mosteller, but `RuntimeError` for Rao-Kupper. Code written to catch one won't catch the
other. **Suggested fix:** harmonize on one exception type (or a shared custom exception class) for
this specific, semantically-identical failure across `mixle/stats/rankings/`.

### FU-07 · `graph_connected` diagnostic doesn't test the condition that actually gates `pseudo_count`
**Tester B.** The Bradley-Terry family's identifiability failure is governed by the *directed* Ford
(1957) condition (does every proper subset of competitors contain someone who beat someone outside
it), not simple undirected "did everyone play everyone (transitively)" connectivity. The
`graph_connected` diagnostic field checks the latter, so it can read `True` on a fit that still
needed (or would have needed) regularization. The correct information exists elsewhere
(`regularized`/`pseudo_count` fields on the same diagnostics object) — this is a naming/scoping
problem, not a missing feature. **Suggested fix:** rename the field to describe what it actually
checks, and/or add a field that directly reports the real (directed) identifiability condition.

## Documentation-only

### FU-08 · No guidance on choosing `pseudo_count` for Bradley-Terry-family regularization
**Tester B.** Unavoidable for any realistic dataset with a dominant, undefeated result. Sweeping
0.05→2.0 left the top rankings stable but flipped the order of two near-tied bottom competitors and
changed the leader's worth margin by ~10x. Not a bug — a real interpretability gap the docstrings
don't warn about.

### FU-09 · `mixle.describe()` on a raw array gives a thin, unhelpful result
**Tester A.** The package's own top-level docstring pitches `mixle.describe(x)` as the universal
first move, "works on any object." On a raw numpy array of real data — an extremely natural first
try before fitting anything — it returns `"ndarray — no catalogued capability detected"`. A
first-time user following the docs literally could conclude the library has nothing for their data
when `mixle.propose()` is what they actually wanted.

### FU-10 · `dump_models()` docstring doesn't mention the `Model` wrapper needs unwrapping
**Tester A.** `dump_models()`'s docstring says it serializes "a stats model or collection of
models." The object `mixle.propose()` actually returns is a `mixle.Model` wrapper; serializing that
directly raises `SerializationError: callable Model(...) is not registered; use
register_serializable_callable()`. The message names a real escape hatch, but a one-line docstring
note ("if you have a `Model` from `propose()`, pass `model.fitted`") would save the detour.

### FU-11 · `propose()`'s mixture-hint disclaimer is unconditional, diluting it when it matters most
**Tester A.** `propose()` prints the same boilerplate note on every call ("pairwise hints are
unconditional; latent mixture/state/topic structure can explain or hide them"), including the
exact case (genuinely bimodal two-population data) where that warning is the single most important
thing to notice. Because it's identical every time, it's easy to skim past precisely when it's not
boilerplate.

## Flagged, not confirmed as a defect — needs the release owner's own judgment

### FU-12 · Two-population GeneralizedPareto mixture not recovered even via the documented remedy
**Tester A.** A synthetic 2-component GPD mixture (two different heavy-tail "fault systems") was
not recovered by `MixtureEstimator` even after following the library's own documented fix
(`init="dirichlet"` + `best_of` restarts) — it converged to two near-identical middling components
instead of the two true ones. Notably, the tester found the *true* generating mixture did not score
better on held-out log-likelihood than the wrong fit, which suggests this may be a genuinely hard
identifiability problem (two overlapping heavy tails sharing one threshold) rather than a mixle
defect. No diagnostic currently flags "this recovered mixture might be wrong" — a user would need
an independent check like the tester's own held-out comparison to notice. Needs someone with
mixture-identifiability expertise to assess before deciding whether this is fixable at all.

## Trivial

### FU-13 · `fit_diagnostics.l1_change` changes numpy dtype across a JSON round-trip
**Tester B.** `numpy.float64` becomes plain `float` after `to_json()`/`from_json()`. Value is
bit-identical; only the Python wrapper type changes. Cosmetic.
