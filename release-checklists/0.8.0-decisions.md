# 0.8.0 Release Decision Log

Append-only record of 0.8.0 scope changes, waivers, API breaks, benchmark-methodology changes, and claim
changes (worklist **G0.2**). The rule: **no release decision lives only in a PR thread or a local note** —
if it changes scope, breaks an API, waives a P1, or changes a published claim or a benchmark method, it gets
an entry here.

Each entry records: **date · decision · alternatives · evidence · owner · reviewer · expiration · worklist
ID**. Entries are added, never edited in place (correct a decision with a new superseding entry). A decision
proposed in an open PR is recorded with **reviewer: pending**; it becomes **accepted** when that PR is
reviewed and merged into `release/0.8.0`.

Owner is the release owner (grant.boquet@gmail.com) unless stated. Dates are UTC.

---

## D-0001 · Drop Python 3.10; floor numpy ≥ 2.4, scipy ≥ 1.16

- **Date:** 2026-07-11
- **Decision:** Raise `requires-python` to `>=3.11` and the runtime floors to `numpy>=2.4`, `scipy>=1.16`,
  `mpmath>=1.3`; drop the 3.10 classifier and set `ruff`/`mypy` targets to py311.
- **Alternatives considered:** keep 3.10 + older floors (rejected: scipy<1.13 `von_mises` precision, numpy
  2.0.0 `IndexError` bugs, numpy<2.4 t-SNE/atlas fragility, and tests using numpy-2.0-only `np.trapezoid`
  all failed the min-version job); pin exact versions (rejected: floors, not pins, keep newer majors usable).
- **Evidence:** min-versions CI job bisecting the true floor; 4252 tests pass at the new floors.
- **Reviewer:** pending — PR #310
- **Expiration:** revisit at 0.9.0 (numpy/scipy floors move forward as the ecosystem does).
- **Worklist:** S13.4

## D-0004 · Deprecation policy: warn, keep ≥ 2 minor releases, then remove

- **Date:** 2026-07-11
- **Decision:** A deprecated stable name emits a `DeprecationWarning` (one message format), keeps working and
  forwarding unchanged, and is removed no earlier than two minor releases after the announcing release
  (announced in 0.8.0 → removable no earlier than 0.10.0). Removal ships a migration note/example.
- **Alternatives considered:** remove-on-next-minor (rejected: too aggressive for stable names); never remove
  (rejected: unbounded compatibility debt).
- **Evidence:** the mechanism + policy doc; a static test that every "Deprecated alias" callable warns.
- **Reviewer:** pending — PR #324
- **Expiration:** none (standing policy).
- **Worklist:** A1.5

## D-0006 · Coverage gate is a conservative catastrophic-regression floor (45%), not a target

- **Date:** 2026-07-11
- **Decision:** Add `--cov-fail-under=45` to the base-install `full` CI job. This is a floor set well below
  the real number (the fast suite alone covers ~72% locally with backends installed) so it trips only on a
  large regression (e.g. a dropped test directory), not on ordinary changes. Raise it once the optional
  extras job also reports coverage and the two are combined.
- **Alternatives considered:** no coverage gate (rejected: no regression tripwire); a threshold near the true
  number (rejected: base install skips optional backends, so it would misrepresent and block unrelated PRs).
- **Evidence:** measured fast-suite coverage 72% with `branch=true`; base-only is lower but well above 45%.
- **Reviewer:** pending — PR #334
- **Expiration:** revisit when the combined (base + optional) coverage number exists.
- **Worklist:** T3.4

## D-0009 · Deploy pure models as safe JSON; keep pickle only for torch-backed models

- **Date:** 2026-07-11

## D-0010 · `mpmath` narrows to an optional extra; D-0001's floor bump did not justify a base dependency

- **Date:** 2026-07-17
- **Decision:** Move `mpmath` out of base `dependencies` into a new `highprec` extra (`mpmath>=1.3`, floor
  unchanged). `mixle.engines.highprec` is mpmath's only non-test consumer, and it already treated mpmath as
  optional (`try: import gmpy2 / except: try: import mpmath / except: _BACKEND=None`, preferring the
  correctly-gated `gmpy2` extra); forcing mpmath into every install made that `_BACKEND=None` degrade path
  practically unreachable and contradicted the base-install optional-dependency convention this project
  otherwise enforces (worklist P2.2).
- **Relationship to D-0001:** D-0001 (2026-07-11) raised the runtime floor to `numpy>=2.4, scipy>=1.16,
  mpmath>=1.3` as one bundled decision. Its own "Alternatives considered"/"Evidence" sections cite only
  numpy/scipy-specific bugs (von Mises precision, IndexError, t-SNE/atlas fragility); mpmath is never
  mentioned again after the initial line, and the `dependencies` array's comment block in `pyproject.toml`
  never stated a rationale for mpmath specifically. D-0001's floor (`>=1.3`) is unchanged and still correct;
  this entry narrows only the base-vs-optional placement, which D-0001 never analyzed on its own merits.
- **Alternatives considered:** leave mpmath in base deps (rejected: contradicts P2.2, makes
  `_BACKEND=None` unreachable in any real install, no evidence anywhere it was a deliberate choice on its
  own merits); fold mpmath into the existing `gmpy2` extra (rejected: `gmpy2`'s own primary consumer is
  unrelated -- `mixle/enumeration/quantization/core.py`'s structural count-DP -- and the two are
  alternative backends for the same feature, not a bundled pair like `torch`+`safetensors`; a dedicated
  `highprec` extra names the feature it unlocks, matching `arrays`/`grammar`/`data`).
- **Evidence:** clean wheel install (neither gmpy2 nor mpmath) -- `highprec._BACKEND is None`,
  `available() is False`, `_require()` raises `RuntimeError` (not `ImportError`), and the 768-module public
  import sweep (`scripts/import_sweep.py`, worklist P2.1) passes clean. Wheel install with the new
  `highprec` extra (mpmath present, gmpy2 absent) -- `_BACKEND == "mpmath"`, correct `hp_sum`/`hp_array`
  results. Targeted run of every file this change touches: 38 passed, 18 subtests passed, 0 failed.
- **Reviewer:** pending — PR #525
- **Expiration:** none (corrects a placement error; no scheduled revisit).
- **Worklist:** P2.2

## D-0016 · Narrow the automatic-modeling docs instead of wiring propose() into optimize()'s structure search

- **Date:** 2026-07-24
- **Decision:** `propose()`'s candidates (the heuristic recommendation, the independence baseline, and an
  optional LLM design) each already build a concrete estimator before fitting, so none of them reach
  `optimize()`/`fit()`'s own no-estimator (`estimator=None`, `structure="auto"`) auto-structure-search
  path — the only route to a copula or learned-Bayesian-network dependence upgrade. `propose()`'s only
  dependence-capturing candidate is a joint multivariate-Gaussian estimator, and only for fixed-length,
  fully-observed, purely-numeric vector rows (never tuples) — narrower than what `optimize(data)` reaches
  directly. `docs/automatic-modeling-contract.rst`'s "Dependence between fields" section named only
  `optimize(data)`, correctly, but sat immediately above a "Selection and validation" section describing
  `get_estimator(data)`/`propose(data)` with nothing distinguishing their (much narrower) reach — an easy
  misread, and `propose()`'s own docstring called its heuristic recommendation "dependency-aware" with no
  such qualification. Reworded both to state the boundary explicitly; no code or search-budget behavior
  changed. `mixle/tests/lifecycle_test.py::test_propose_frontier_does_not_reach_the_copula_dependence_upgrade`
  pins the current asymmetry directly against `mixle/tests/automatic_copula_structure_test.py`'s own
  dependent-heterogeneous fixture, so a future change on either side of the gap has to touch this test
  deliberately rather than let the docs claim silently drift.
- **Alternatives considered:** wire the structure search into `propose()`'s candidate list (rejected for
  *this* pass, not rejected outright — real, unresolved design cost: `_maybe_structured_model` does its
  own internal multi-candidate fitting, so `propose()`'s `max_candidates`/`timeout` budget accounting
  would double-count or need reconciling; both `propose()`'s own candidate construction and
  `_maybe_structured_model` independently call `get_estimator(rows)` and fit a composite, duplicating
  work; `optimize()` called with `estimator=None` returns a fitted distribution directly, not a fit-ready
  `ParameterEstimator` the way `propose()`'s other candidates work, so the frontier's own bookkeeping
  shape doesn't fit without a real design decision; `Model.fit()`'s later re-fit-on-full-data call
  (`optimize(fit_data, self.spec, ...)`) always passes a concrete `self.spec`, so it would need its own
  special-casing too. None of this is mechanical — matches D-0011's precedent of narrowing a claim rather
  than forcing the larger, not-yet-designed work into a release-prep pass under time pressure); leaving
  the docs as they were (rejected: `docs/automatic-modeling-contract.rst` is the evidence cited for
  section 5's "Public automatic-modeling contract: COMPLETE" gate, so an imprecise contract page leaves
  that COMPLETE status overstated).
- **Evidence:** direct reproduction — `optimize(data, out=None)` on strongly-dependent (r=0.85),
  heterogeneous-marginal (Gamma/Normal) tuple data returns a `CopulaDistribution`; `mixle.propose(data,
  fit=True)` on the identical data returns a frontier whose only estimator type is `CompositeEstimator`.
  New regression test passes; full sweep across `lifecycle_test.py`, `propose_budget_test.py`,
  `automatic_copula_structure_test.py`, `task_recommend_test.py`, `automatic_test.py`,
  `automatic_datumnode_edgecases_test.py`, `automatic_modality_routing_test.py`, and
  `signature_docstring_sync_test.py` (80 tests) passes; `sphinx -b dummy` build clean (also fixed a
  genuinely broken `:doc:` cross-reference from the docstring — relative doc-role resolution from a
  Python docstring needs a leading `/` to resolve against the source root, not the docstring's own
  virtual document path; confirmed via the dummy build's `ref.doc` warning before and its absence after).
- **Reviewer:** pending — final 0.8.0 preparation PR.
- **Expiration:** none for the docs narrowing itself; revisit if/when a future release takes on the larger
  wiring work, per the design costs listed above.
- **Worklist:** I6 (automatic modeling), X12 (documentation, claims)

## D-0017 · Supersede D-0016: wire the structure search into propose() after all

- **Date:** 2026-07-24
- **Decision:** Reverses D-0016. `propose()`'s candidate list now includes `("structured", None)` --
  `optimize()` called with no pre-built estimator, i.e. its own no-estimator auto-structure-search, the
  route to a copula/learned-Bayesian-network dependence upgrade. Every design cost D-0016 raised turned
  out to already be solved by existing, first-class plumbing once actually checked rather than assessed
  from a read of the code: `propose()`'s scoring loop already calls `optimize(train, est, ...)` per
  candidate, so `est=None` reaches the auto-structure-search path with zero special-casing; `Model.spec`
  already defaults to `None` and is documented as "the estimator is inferred at fit time"; `Model.fit()`'s
  `optimize(fit_data, self.spec, ...)` already re-runs structure search correctly on a later re-fit
  (verified directly: `Model(None).fit(data)` and a second `.fit()` on more data both worked, first try);
  each candidate participates in `max_candidates`/`timeout` as one slot regardless of how many structures
  it tries internally, exactly like every other candidate, because the loop already iterates
  `(name, estimator)` pairs one at a time. None of D-0016's four cited costs were real blockers once
  tested against the actual code rather than reasoned about from its shape.
- **Why reconsidered:** an independent review scored the gap D-0016 left open as the most serious release
  blocker, not a documentation nit, with a quantified, reproducible cost: on `examples/quickstart_example.py`'s
  own dependent dataset (`category` driving both `amount`'s mean and `flag`'s rate — written specifically
  to demonstrate `propose()`'s dependency detection), `propose()` returned a `CompositeDistribution`
  scoring roughly 1.17 nats/row worse on held-out data than the `HeterogeneousBayesianNetwork`
  `optimize()` finds on the identical data. That example's own accompanying comment already asserted
  propose()'s "dependency detection... should notice" this relationship -- D-0016's docs fix left the
  code silently contradicting comments already shipped in this exact release-prep tree. Re-examining the
  implementation cost under that severity, rather than the abstract "is this in scope" framing D-0016
  used, found the fix was a few lines, not a redesign.
- **Alternatives considered:** keep D-0016's narrowed docs and fix only the quickstart example's comment
  (rejected: papers over the underlying capability gap the review correctly flagged as the actual
  problem, and the README's existing "notice when fields depend on each other... fit a copula or vine
  when continuous columns are correlated" claim -- unchanged since before D-0016, never itself edited --
  would have stayed false for `propose()` specifically); gate the new candidate on row type (tuple-only,
  matching where the BN/copula upgrade actually applies) (rejected as unnecessary: `optimize(train, None,
  ...)` is unconditionally safe on non-tuple numeric-vector rows too, verified directly -- it falls
  through to a plain fit rather than erroring, and the existing per-candidate `try/except` in the loop
  is a safety net regardless).
- **Evidence:** direct reproduction confirmed the finding (`HeterogeneousBayesianNetwork` at held-out
  -1.4263 vs `CompositeDistribution` at -2.2714 on the quickstart's own generator, matching the
  independent review's -1.4263 for the structured model exactly); `propose()` end-to-end now returns the
  `HeterogeneousBayesianNetwork` as the winner on that data; `examples/quickstart_example.py` re-run
  output now matches its own pre-existing narrating comment. `docs/automatic-modeling-contract.rst`,
  `mixle/lifecycle.py`'s `propose()` docstring, `docs/lifecycle.rst`, and `docs/package-map.rst` updated
  to describe the restored capability; `mixle/tests/lifecycle_test.py`'s D-0016-era test (asserting the

## D-0025 · `enumeration.streams.freeze()` keys are type/dtype-aware, not Python-equality-aware

- **Date:** 2026-07-25
- **Decision:** `mixle/enumeration/streams.py`'s `freeze()` (the canonical hashable dedup key used
  across every union, distinct-stream, and mass-certificate enumeration path) now includes dtype in
  ndarray keys (`(shape, dtype.str, bytes)` instead of `(shape, bytes)`) and tags every other value by
  `(type(x), x)` instead of bare `x` (MXR-080-0198). An external review found `tobytes()`-only ndarray
  keys let an `int8` array holding `-56` and a `uint8` array holding `200` collide (both encode to the
  single byte `0xc8`), and bare-scalar keys let Python's native cross-type equality collapse
  `freeze(True) == freeze(1)` and `freeze(False) == freeze(0)` — even though a typed distribution's
  support can legitimately contain both a bool and an int (or an int and a float) as distinct outcomes.
  The new policy makes type part of a value's dedup identity unconditionally: `freeze(1) != freeze(1.0)`
  is now also true, as a direct, deliberate consequence of the same single rule, not a separate special
  case. NaN is the one documented exception — every NaN float still collapses to one shared sentinel
  regardless of origin, since IEEE 754 `nan != nan` would otherwise make each NaN a unique,
  never-deduplicated key, which is not the desired dedup behavior for a "missing/undefined" value.
- **Alternatives considered:** keep bare-value keys and special-case only the reported `bool`/`int`
  collision (rejected: leaves every other Python cross-type equality — `1 == 1.0`, `Decimal` vs `int`,
  etc. — silently colliding too; the finding's own remediation asked for "a single documented cross-type
  equality policy," not a one-off patch); make `freeze()` idempotent on its own tagged output by
  detecting and stripping a prior `(type, value)` tag before re-tagging (rejected: a tagged key's shape
  is not reliably distinguishable from a legitimate user value that happens to look like one — e.g. a
  genuine 2-tuple support value — so "is this already frozen" can't be decided safely from the value
  alone; fixing the one real caller that depended on accidental idempotence is a smaller, more honest
  fix than adding an ambiguous self-detection rule to the primitive every enumeration path relies on).
