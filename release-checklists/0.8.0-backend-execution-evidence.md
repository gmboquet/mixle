# 0.8.0 backend execution evidence

Retained execution evidence for the distributed backends `docs/backend-support.rst` labels
**"Tested, not CI-gated"** — MPI, Spark, Ray and Lightning — plus the optional-CI routes. That label
exists because those backends are installed in no CI lane, so a regression in them would not be
caught automatically. This file is the counterpart the label asks for: the backends were actually
run, on a real installation, and the commands and versions are recorded so the run can be repeated.

## What this is, and what it is not

This is **implementer-produced execution evidence**, not an independent systems review. It records
that the routes execute and agree with the local backend on this machine. It does **not** discharge
the E14.3 systems-review gate, which requires a reviewer other than the implementer working from a
clean clone, and which explicitly states that one local backend cannot clear it.

Read it as: "these backends were exercised and this is exactly how" — not "these backends are
certified."

### MPI numerical agreement, run directly under `mpiexec`

The backend-matrix tests assert agreement internally; this is the same claim made visible, because
"scale with a flag" is only worth anything if the distributed fit equals the local one:

```
mpiexec -n 2 python mpi_probe.py

  ranks=2  local=(4.9428960096, 3.9056520032)  mpi=(4.9428960096, 3.9056520032)
  agree to 1e-10: True
```

A Gaussian fit over 400 observations, two ranks, tree-fold reduction of sufficient statistics.
Exact agreement with the serial fit to 1e-10 on both parameters.

## GPU (Metal / MPS) — it runs, and it does NOT match CPU

This machine is an Apple M4 (10 GPU cores). `torch.backends.mps.is_available()` is true;
**CUDA is not available**, so the `Torch (CUDA / GPU)` row stays *Hardware-gated / Unverified* —
Metal is a different backend and this evidence says nothing about CUDA.

What was verified is the `Torch (CPU)` row's claim that GPU is reachable "via device argument":

```python
NeuralDensityEstimator(build_vae(4, latent=2), device="mps")
optimize(data, est, max_its=3)      # fit completes; parameters live on mps:0
```

That works. But the GPU and CPU paths **do not agree numerically**, and the gap is larger than a
reader would assume. Same seed, same architecture, same data; total per-observation log-density
compared across devices:

| optimizer iterations | max abs difference | max relative |
|---|---|---|
| 1 | 1.91e-01 | **2.2e-02** |
| 3 | 2.48e-01 | 3.4e-02 |
| 10 | 3.39e-01 | 4.2e-02 |

The divergence is already ~2% relative after a *single* iteration and grows only mildly after that,
so this is not chaotic amplification of a tiny difference through the optimizer — it is a
kernel-level float32 difference between the MPS and CPU implementations, present from the first
step, with mild accumulation on top.

Consequences, stated plainly:

* A GPU fit is **not** a drop-in reproduction of a CPU fit. Anything that pins a log-density, a
  fitted parameter, or a model digest computed on CPU will not match the same computation on MPS.
* `mixle.inference.reproduce` fingerprints parameters, so a receipt recorded on one device will not
  verify on the other. That is correct behaviour — the fits genuinely differ — but it is a trap if a
  user assumes `device=` is a performance knob rather than a numerical one.
* Any future promotion of a GPU row needs a stated **tolerance**, not an equality claim.

This was not previously measured or documented. It is recorded here rather than in the support
matrix's claim columns because it is a property of the torch/MPS stack, not a mixle defect.

## Limits of this evidence — read these before citing it

* **One machine, one OS, one architecture.** macOS arm64. Nothing here says anything about Linux
  x86_64, which is the platform the CI baseline and most users run.
* **One process topology.** Every "distributed" run here is multi-process on a single host. No
  multi-node run and no real network transport. `docs/backend-support.rst` already places
  frontier-scale multi-node/multi-GPU training out of scope for 0.8.0, and this evidence does not
  extend it.
* **No interruption, corruption, or rollback testing.** The systems-review protocol requires
  checkpoint interruption/recovery, corrupted-artifact rejection and rollback behaviour. Those are
  not covered here.
* **Not independent.** See the note at the top.

## Reproducing it

The backends are not in the release venv; they are installed in the development environment at
`mixle/.venv` (Python 3.12.12). Point `PYTHONPATH` at the candidate worktree and use that
interpreter. `MIXLE_RUN_TORCHRUN_SMOKE=1` is required to un-gate the torchrun smoke tests, which
skip by default.
